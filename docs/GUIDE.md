# Memora Engine: от подключения до первого диалога

[English](GUIDE.en.md) · [API](API.md) · [Патч для сайта Memora](INTEGRATION.md)

## 1. Какую задачу решает ядро

Memora Engine — встраиваемая JavaScript-библиотека, не чат-платформа и не модель. На входе — история активной ветки, правила игрока, сохранённые факты и изменения сцены. На выходе — текст контекста, который ваше приложение добавляет к запросу модели. Ядро работает без API-ключей и внешних npm-зависимостей. Встроенные шаблоны и команды игрока сейчас русскоязычные.

Ядро не хранит аккаунты, не вызывает провайдера, не отправляет потоковые ответы и не решает, кому доступен приватный канон. Это делает адаптер вашего приложения. Условия использования и пример видимой ссылки описаны в [Attribution](ATTRIBUTION.md).

## 2. Подключение

Скопируйте `roleplay-engine.js` из вашей версии репозитория. Библиотеку можно использовать напрямую, установка npm-пакета не нужна. Для воспроизводимых сборок закрепите конкретный коммит.

**Node.js, CommonJS:**

```js
const engine = require('./roleplay-engine.js');
const context = engine.buildPersonalContext({ history: [] });
```

**Node.js, ESM:**

```js
import { buildPersonalContext } from './roleplay-engine.js';
const context = buildPersonalContext({ history: [] });
```

Если ваш проект задаёт `"type": "module"`, сохраните CommonJS-файл как `roleplay-engine.cjs` и импортируйте по этому пути.

**Браузер:** загрузите ядро обычным скриптом раньше кода приложения.

```html
<script src="./roleplay-engine.js"></script>
<script>
  const engine = window.MemoraRoleplayEngine;
  console.log(engine.buildPersonalContext({ history: [] }));
</script>
```

Ключ модели держите на сервере. Браузер может собрать контекст, но не должен получать серверные ключи и закрытые данные персонажа.

## 3. Личный чат: жизненный цикл хода

1. Загрузите активную ветку. Сохраните `role`, `content`, стабильный `createdAt` и активную версию каждой реплики. Не подменяйте время сообщения при загрузке: оно участвует в отпечатке источника.
2. Добавьте сообщение игрока. Передайте данные ветки в `buildPersonalContext`. Например, «Запомни: пиши от третьего лица» станет правилом текущей ветки. «В следующем ответе …» действует для последнего пользовательского хода, включая его повторную генерацию.
3. На сервере соедините контекст с каноном, который разрешено использовать, и активными репликами. Ядро не выбирает формат API: роли запроса, вложения и лимиты определяет ваш адаптер. Не представляйте факт из памяти как доверенную системную команду.
4. Поток и повторы обрабатывайте в провайдерном адаптере. Незавершённый ответ можно показать игроку, но не делайте его источником памяти.
5. При успешном ответе сохраните реплику. В фоне возьмите `recentFactMessages(history)`, подготовьте `buildFactExtractionPrompt` и разберите ответ через `parseFactExtractionResponse` и `parseSceneUpdate`. Перед записью снова проверьте владельца ветки (если нужно), идентификатор сессии и неизменность версии. Привяжите факты и запись сцены к отпечаткам анализируемых реплик через `memorySource`. Не сохраняйте результат после удаления ветки.

Рабочий адаптер с локальной заглушкой: [`examples/chat-adapter.cjs`](../examples/chat-adapter.cjs). Он проверяет полный ход, устаревший результат анализа и смену варианта — без сети и ключей.

## 4. Правки, ветки и удаление памяти

- **Правка/свайп:** передайте только активную версию реплики. Старый факт с `sources` больше не попадёт в контекст, а зависимое изменение сцены не применится. Записи без `sources` остаются совместимыми, но не могут автоматически откатиться.
- **Развилка:** создайте новый идентификатор сессии и копию истории до точки ветвления. Не делите изменяемые массивы между родителем и дочерней сессией. Переносите только память, допустимую для среза; исключения и закреплённые записи копируйте по правилам продукта.
- **Удаление правила или факта:** храните исключения отдельно от истории. Для правила используйте `source`, для факта — `normalizeMemoryText(content)`. Удаление из памяти не требует стирать переписку. Если разрешено повторное извлечение, применяйте исключения и при записи, и при сборке контекста.
- **Длинные диалоги:** лимиты секций ядра выражены в символах или количестве записей, не в токенах. Токены считайте по выбранной модели. Хранилище, которое выбрасывает ранние реплики, может удалить источник давнего правила или сцены; не путайте сокращение запроса к модели с удалением истории.

## 5. Групповой чат

Ваш код выбирает адресата и участника, стоящего в очереди, затем передаёт их в `buildGroupContext` вместе с режимом и его названием. При прямом обращении адресат важнее очереди. После успешного ответа спросите `shouldAdvanceQueue(settings, addressedParticipant)`, надо ли двигать указатель. Не двигайте его при обрыве или повторе того же хода. Личная память автоматически в группу не переносится. Если один герой не должен знать секрет другого, отфильтруйте его **до** отправки запроса.

## 6. Проверка и отладка

```sh
node --test core.test.cjs
node examples/first-scene.cjs
node examples/chat-adapter.cjs
```

| Симптом | Что проверить |
|---|---|
| Ядро не найдено в браузере | Порядок скриптов и успешную загрузку `roleplay-engine.js`. |
| Правило не появилось | `role: 'user'`, явную команду, активную ветку и списки исключений. |
| Факт исчез после перезагрузки | Не изменились ли `createdAt` или `content`, сохранились ли источники. |
| Старый факт вернулся после свайпа | Передаётся ли только активный вариант, проставлены ли `sources`, отбрасывается ли запоздавший анализ. |
| Модель игнорирует правило | Проверьте фактически отправленный контекст и его обрезку. Передача правила не гарантирует выполнение моделью. |

Перед выкладкой прогоните как минимум смену варианта, ответвление, обрыв и восстановление ответа, длинную историю после перезагрузки и отсутствие данных другой ветки. Для тестов используйте синтетические диалоги; не пишите частные переписки и ключи в диагностические логи.
